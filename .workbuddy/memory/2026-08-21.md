### 20:20 用户对比桌面灵项目: 为什么人家语音稳定我们却偶发卡死

**参考项目**: https://github.com/qiyueblues-design/zhuomianling (桌面灵 v1.5.0, Electron+React+Live2D+GPT-SoVITS)

**桌面灵的 TTS 架构** (阅读其 `src/main/services/speech/textToSpeech.ts` 源码):
- 调用 **GPT-SoVITS 官方 API 服务** (api_v2.py, 常驻 127.0.0.1:9880, POST /tts, 标准 HTTP)
- **不自己写 worker 脚本**, 模型常驻显存由 API 服务管理
- **预热机制**: `warmUpTextToSpeech()` 连接时合成极短句"嗯。"/"うん。"/"Mm." 热身, 首句不慢
- **45秒超时**: `textToSpeechTimeoutMs = 45_000`, AbortController 四种取消原因 (renderer/owner-destroyed/replaced/timeout)
- **主动取消**: 新请求替换旧请求, 渲染进程销毁自动 abort
- 语音失败降级为文字聊天, 不影响主流程
- 非流式 (`streaming_mode: false`), 但响应完整可靠

**我们的架构问题** (server.js + tts_worker.py):
- 自写 stdin/stdout 二进制协议 worker, 单进程串行
- **无预热** → 闲置后首句慢
- **无超时/看门狗** → worker 卡死时前端永远"正在合成音频"
- **stdin 管道死锁** 已多次复现 (多 worker 互锁)
- 对比结论: 桌面灵稳定不是模型差异 (同为 GPT-SoVITS), 而是**调用架构差异**

**改进方向** (待用户确认后实施):
1. 换用 GPT-SoVITS 自带 api_v2.py 作为 TTS 服务 (HTTP 调用)
2. 或最小改动: server.js 加超时+看门狗+worker 自动重启+启动预热
