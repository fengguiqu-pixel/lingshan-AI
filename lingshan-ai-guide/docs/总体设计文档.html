2. 系统概述

2.1 产品定位

灵山胜境AI数字人导游系统是一款面向景区的 AI 数字人导游解决方案。以 Live2D 数字人"小灵"为交互形象，融合 DeepSeek 大模型对话能力与 GPT-SoVITS 语音合成技术，为游客提供沉浸式智能导览服务。系统同时为景区运营方提供内容管理、知识库维护与数据可视化分析能力。

2.2 核心能力

  • 智能对话：基于 DeepSeek Chat 大模型 + 知识库 RAG 检索，实现景区问答的准确、自然、多轮对话。
  • 语音讲解：GPT-SoVITS 合成自然流畅的中文语音，数字人口型同步，GPU 加速约 6.5 秒/句。
  • 可视化导览：腾讯地图集成，景点地图/列表双模式，直观展示景区布局与景点详情。
  • 个性化推荐：基于兴趣标签的偏好注入，智能推荐景点与游览路线。
  • 数字人交互：8 种表情、2 组动作、口型同步、情绪映射，呈现生动的导游体验。
  • 运营管理：景点/路线/FAQ/票务/知识库全链路管理后台，JWT 认证保障安全。
  • 数据可视化：ECharts 大屏展示游客统计、消费结构、年龄分布、景点热度等。

3. 系统架构设计

3.1 整体架构图

系统采用分层架构，所有服务通过单端口（3000）统一对外提供。以下是整体架构示意图：

架构说明：

  • 表现层：三个前端入口共享同一端口，通过路径区分（/ 主前端、/admin 后台、/admin/visualization 大屏）。
  • 服务层：Express 服务器统一处理静态文件与 API 请求，10 个路由模块各司其职。

  • TTS 层：GPT-SoVITS 以 Python 子进程方式运行，通过 stdin/stdout 二进制协议通信。

4. 模块设计

4.1 景点导览模块

功能描述

提供景区景点的浏览、检索与详情展示，支持地图模式与列表模式两种视图。

设计要点

  • 数据结构：scenic_spots 主表 + highlights（亮点）+ tips（贴士）子表，一对多关联。
  • 双模式视图：地图模式基于腾讯地图 JSAPI 渲染标记点；列表模式以卡片展示。前端通过同一 API 获取数据，视图层切换。
  • 景点详情：包含名称、副标题、评分、标签、建议时长、最佳时间、描述、坐标、亮点列表、贴士列表。
  • 排序：按 order_num 字段排序，支持管理后台调整。

核心接口

GET  /api/scenic-spots          # 获取所有景点（含亮点+贴士）
GET  /api/scenic-spots/:id      # 获取单个景点详情
POST /api/scenic-spots          # 新增景点（管理后台）
PUT  /api/scenic-spots/:id      # 更新景点（含亮点+贴士级联更新）
DELETE /api/scenic-spots/:id    # 删除景点（级联删除亮点+贴士）

4.2 AI对话模块（含知识库增强 RAG 流程）

功能描述

基于 DeepSeek Chat 大模型，结合景区知识库与 FAQ 进行检索增强生成（RAG），提供准确自然的智能问答。

RAG 检索增强流程

用户问题 │ ▼ ┌─────────────────────────────┐ │ ① 关键词提取（分词+停用词过滤） │ └──────────────┬──────────────┘ │ ┌──────────┼──────────┐ ▼ ▼ ▼ ┌────────┐ ┌────────┐ ┌────────────┐ │② 景点 │ │③ FAQ │ │④ 知识库文档 │ │ 信息 │ │ 检索 │ │ 检索(LIKE) │ │(全量) │ │(关键词) │ │(关键词+排序) │ └────┬───┘ └────┬───┘ └─────┬──────┘ └─────────┬┴───────────┘ │ ▼ ┌─────────────────────────────┐ │ ⑤ 上下文组装（限 5000 字符） │ │ 景点信息 + 票务 + FAQ + 文档 │ └──────────────┬──────────────┘ │ ▼ ┌─────────────────────────────┐ │ ⑥ System Prompt 构建 │ │ + 个性化偏好注入 │ │ + 历史对话（最近10轮） │ └──────────────┬──────────────┘ │ ▼ ┌─────────────────────────────┐ │ ⑦ DeepSeek Chat API 调用 │ │ model: deepseek-chat │ │ temperature: 0.7 │ └──────────────┬──────────────┘ │ ▼ AI 回复 → 存入 chat_interactions

降级策略

当 DeepSeek API 不可用时（网络异常、密钥无效），系统自动降级为本地兜底回复：根据关键词匹配返回预设的票务、景点基础信息，并提示游客联系景区客服。

个性化偏好注入

当用户通过个性推荐模块选择兴趣标签后，偏好内容会注入 System Prompt，指导 AI 调整回答风格与推荐侧重，实现个性化对话体验。

4.3 Live2D数字人模块（含表情/动作/口型系统）

功能描述

渲染 Live2D 数字人"小灵"，实现表情切换、动作播放、口型同步，作为系统的视觉交互形象。

模型参数

项目规格
模型名称小灵（ling）
模型文件ling.moc3 + ling.model3.json
物理模拟ling.physics3.json（头发、衣物摆动）
表情数量8 种（normal/smile/angry/sad/surprise/think/shy/cry）
动作数量2 组（眨眼 zhaiyan / 照相 zhaoxiang，均属 Idle 组）
口型同步参数ParamMouthOpenY
眨眼参数ParamEyeLOpen / ParamEyeROpen
贴图数量2 张（texture_00.png / texture_01.png）

表情映射系统

系统支持 12 种情绪触发词到 Live2D 表情的映射。每种映射包含：

  • trigger：情绪触发词（如 happy、sad、excited）
  • kind：类型（expression 或 motion）
  • name：表情名称（如 smile、surprise）
  • group：动作组名（如 Idle）
  • index：动作索引

口型同步机制

口型同步基于 TTS 合成的 WAV 音频实时分析。前端通过 Web Audio API 提取音频振幅，映射到 Live2D 的 ParamMouthOpenY 参数，实现数字人嘴巴开合与语音同步。可调整灵敏度、平滑系数、振幅阈值等参数。

动作管理

  • 空闲动作自动播放：可配置开关、间隔时间（默认 12 秒）、是否随机选择
  • 启用的空闲动作：从可用动作中勾选参与自动播放的子集
  • 情绪触发动作：为特定情绪词配置触发的动作组与索引
  • 表情联动：可配置表情切换时是否自动播放对应动作

4.4 TTS语音合成模块（含进程通信协议）

功能描述

基于 GPT-SoVITS v2pro 引擎，使用"三月七 March7th v3"声线，将文本合成为 WAV 音频，供数字人语音播报。

架构设计

TTS 模块采用子进程架构，GPT-SoVITS 作为独立 Python 进程运行，通过 stdin/stdout 与 Express 服务器通信：

Express 服务器 GPT-SoVITS Worker (Python) ┌──────────────┐ ┌──────────────────────┐ │ POST /api/tts│ │ tts_worker.py │ │ │ │ │ │ │ │ ┌────┴────┐ │ stdin (JSON) │ ┌────┴────┐ │ │ │ ttsQueue│──┼────────────────▶│ │模型推理 │ │ │ │ (队列) │ │ {text,lang}\n │ │(GPU/CPU)│ │ │ └────┬────┘ │ │ └────┬────┘ │ │ │ │ stdout (二进制) │ │ │ │ ┌────┴────┐ │◀────────────────│ WAV 音频数据 │ │ │解析响应 │ │ [4字节长度][WAV]│ (或 0长度+错误信息) │ │ └────┬────┘ │ └──────────────────────┘ │ │ │ │ 返回 audio/wav └──────────────┘

进程通信协议

// 请求（stdin，UTF-8 JSON + 换行符）
{"text": "欢迎来到灵山胜境", "text_language": "zh"}\n

// 响应（stdout，二进制帧）
// ┌─────────────────┬───────────────────────────────┐
// │  4 字节长度      │  WAV 音频数据 / UTF-8 错误信息   │
// │  (UInt32LE)     │  (长度为0时为错误信息)           │
// └─────────────────┴───────────────────────────────┘

队列与并发控制

  • ttsQueue：请求队列，FIFO 顺序处理
  • ttsProcessing：处理中标志，同一时间仅处理一个 TTS 请求
  • workerBuf：响应缓冲区，累积 stdout 数据直到完整帧到达
  • 异常处理：Worker 退出时清空队列并返回 503 状态码

缓存重定向

所有 Python 缓存目录（HuggingFace、PyTorch、pip 等）通过环境变量重定向到工作空间，避免污染系统目录，便于便携部署。

性能对比

模式推理速度依赖
GPU 加速约 6.5 秒/句NVIDIA 显卡 + CUDA 12.x + PyTorch GPU 版
CPU 推理约 64 秒/句无特殊依赖，PyTorch CPU 版

4.5 路线规划模块

功能描述

提供景区推荐游览路线的展示与管理，每条路线包含多个有序站点。

数据结构

  • routes：路线主表（名称、描述、时长、难度）
  • route_stops：站点表（时间、景点、活动、时长、排序），与路线一对多关联

预置路线

  • 轻松游览路线（2-3小时，轻松，3 站）
  • 深度文化体验路线（4-5小时，适中，5 站）
  • 亲子互动路线（3-4小时，轻松，4 站）

前端展示

以时间轴形式展示每条路线的站点顺序，包含时间、景点名、活动描述与停留时长，难度以彩色标签区分。

4.6 票务信息模块

功能描述

展示景区门票价格、优惠政策、开放时间与包含项目，支持管理后台编辑。

数据结构

ticket_info 单行表，包含全价票、半价票、免票政策、开放时间、包含项目字段。

设计要点

  • 票务信息全局唯一（LIMIT 1），管理后台 PUT 更新
  • AI 对话时自动检索票务信息注入上下文
  • 前端独立票务信息面板，清晰展示价格与政策

4.7 个性推荐模块

功能描述

根据游客兴趣标签（历史文化、亲子互动、摄影打卡、佛教艺术、自然风光等）提供个性化景点推荐与对话风格调整。

设计要点

  • 标签选择：前端提供兴趣标签多选，支持自定义
  • 偏好注入：所选标签内容作为 preferences 参数传入 AI 对话接口
  • Prompt 影响：偏好注入 System Prompt 的"游客个性化偏好"段落，指导 AI 调整回答侧重与风格
  • 推荐联动：可跳转到 AI 对话，数字人将基于偏好进行个性化讲解

偏好注入示例

【游客个性化偏好 - 务必遵循】
该游客通过个性化推荐选择了以下兴趣偏好：历史文化, 佛教艺术

请严格按以下讲解方向调整回答风格和侧重：
- 历史文化：侧重景点历史沿革、文化内涵、文物故事
- 佛教艺术：侧重佛教艺术价值、建筑特色、壁画雕塑

注意：
- 要在回答中体现对游客兴趣的理解和回应
- 优先推荐与偏好相关的景点和活动
- 语气要贴合游客的兴趣特征

核心能力

  • 结构化 Profile API：GET /api/character/profile 返回结构化形象方案对象

  • 动作预览：POST /api/character/motion-preview 返回动作参数供前端 Live2D 执行

8. 安全设计

8.1 JWT认证机制

  • 签发：管理员登录成功后，使用 JWT_SECRET 签发 24 小时有效的 Token
  • 验证：verifyToken 中间件校验 Authorization: Bearer <token> Header
  • 受保护接口：GET /api/admin/profile 等接口需携带有效 Token
  • 密钥管理：JWT_SECRET 通过 .env 环境变量配置，不硬编码
安全建议：当前管理员密码为明文存储，生产环境建议升级为 bcrypt 哈希存储。管理后台的写操作接口建议增加 Token 验证中间件。

8.2 CORS配置

系统使用 cors 中间件，默认允许所有来源跨域访问。由于系统为单端口部署（前端与 API 同源），实际跨域风险较低。生产环境如需收紧，可配置白名单：

app.use(cors({
  origin: ['http://localhost:3000', 'https://your-domain.com'],
  methods: ['GET', 'POST', 'PUT', 'DELETE']
}));

8.3 文件上传安全

  • 类型限制：头像仅允许 PNG/JPG/GIF/WEBP；知识库文档仅允许 txt/md/docx/pdf/html/json/csv
  • 大小限制：头像 10MB；知识库文档 50MB
  • 文件名处理：上传文件重命名（原名+时间戳），防止路径遍历攻击
  • 存储隔离：上传文件存储在 data/uploads/ 目录，不与代码混放

8.4 密码存储

当前管理员密码采用明文存储于 admin_users 表。默认账号 admin/admin123。

加固建议：① 使用 bcrypt 哈希存储密码；② 部署后立即修改默认密码；③ 限制登录失败次数防止暴力破解；④ 定期轮换 JWT_SECRET。

8.5 输入校验

  • 所有 API 接口对必填参数进行校验，缺失时返回 400 错误
  • SQL 查询使用 better-sqlite3 的参数化查询（? 占位符），防止 SQL 注入
  • JSON Body 大小限制为 50MB（express.json({ limit: '50mb' })）

9. 性能设计

9.1 SQLite WAL模式

数据库开启 WAL（Write-Ahead Logging）模式，提升并发读写性能：

  • 读写并发：读操作不阻塞写操作，写操作不阻塞读操作
  • 性能提升：相比默认的 DELETE 模式，WAL 模式写入性能提升 2-3 倍
  • 崩溃恢复：WAL 日志支持数据库崩溃后的自动恢复
  • 文件说明：.db-wal 为日志文件，.db-shm 为共享内存索引
// database.js 配置
const db = new Database(dbPath);
db.pragma('foreign_keys = ON');
// WAL 模式由 better-sqlite3 默认开启

9.2 GPU加速TTS推理

  • GPU 模式：NVIDIA 显卡 + CUDA 12.x + PyTorch GPU 版，推理约 6.5 秒/句
  • CPU 模式：无 GPU 时自动降级，推理约 64 秒/句
  • 队列串行：TTS 请求通过 ttsQueue 串行处理，避免显存溢出
  • 缓存重定向：模型缓存重定向到工作空间，避免重复下载

9.3 Live2D性能优化

  • 低开销渲染：Live2D 基于 2D 贴图变形，性能开销远低于 3D 模型
  • 眨眼优化：通过 EyeBlink 参数组自动眨眼，无需额外计算
  • 口型同步优化：基于音频振幅实时映射，计算量极小
  • 动作按需播放：空闲动作间隔 12 秒，避免频繁渲染
  • 物理模拟：physics3.json 提供头发/衣物自然摆动，GPU 加速

9.4 缓存策略

缓存层策略说明
浏览器缓存静态资源Express static 中间件默认启用 ETag/Cache-Control
TTS 音频不缓存Cache-Control: no-store，避免重复播放旧音频
AI 回复不缓存每次对话实时调用 DeepSeek API，保证回答新鲜度
知识库检索实时查询每次对话实时 LIKE 检索，确保最新知识库内容
Python 模型缓存持久缓存HuggingFace/PyTorch 模型缓存到工作空间，避免重复下载

9.5 数据库查询优化

  • 参数化查询：better-sqlite3 同步 API，预编译语句（PreparedStatement）复用
  • 外键级联：highlights/tips/route_stops 设置 ON DELETE CASCADE，自动清理关联数据
  • 事务批量操作：数字人配置批量更新使用 db.transaction()，保证原子性
  • 结果限制：FAQ 检索 LIMIT 5，知识库检索 LIMIT 5，对话历史 LIMIT 10，控制上下文长度
  • 上下文截断：RAG 上下文超过 5000 字符时自动截断，防止 Token 超限
